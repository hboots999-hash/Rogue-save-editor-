## 2. Independently testable verification, available today

The existing `verify_offline_sd_hashes.py` compares copied import, backup
and draft to a **protected pre-test original SHA-256** and an **independently
constructed expected candidate digest**; optionally rejects any changes in
the two Phase16 archived files. This is the basic SD integrity gate.

New `verify_raw_draft_diff_v1.py` independently enumerates **every changed
byte in a 131072-byte raw source and draft** and refuses every difference not
pre-authorised in a separate versioned JSON manifest. It reads only, rejects
symlinks/aliases, truncation/oversize, changed files, stale hashes, duplicate
or unsorted offsets, bad JSON/extra fields, and unexpected before/after bytes.
For `move-replacement-research` it limits the declared raw change set to
**eight bytes maximum** (Phase18 research reports an up-to-eight-byte
encrypted move/counter/sector-checksum footprint), but it deliberately does
**NOT** attempt to prove those offsets correspond to a legal Pokémon move or
a valid encrypted GBA save. A manifest copied from the editor's output would
be circular evidence and is NOT independent verification.

Example of a **synthetic, fabricated-only** manifest (create it from an
independent expected toy fixture, *never by diffing the actual editor draft*):

```json
{
  "schema": 1,
  "kind": "move-replacement-research",
  "source_sha256": "64 hexadecimal digits from the protected original",
  "draft_sha256": "64 hexadecimal digits from an independent expected candidate",
  "changes": [
    {"offset": 37, "before": 65, "after": 66},
    {"offset": 65535, "before": 65, "after": 68}
  ]
}
```

The hash strings above are descriptive placeholders, **not executable
values**. Exact byte/offset values must be independently validated for each
fixture and requested edit. When a new move-replacement production contract
eventually exists, the manifest will need to be generated by **a different,
reviewed semantic oracle** that independently decrypts/checks original and
draft Pokémon, confirms species/PID/OT/party slot, move IDs/current PP/PP-Up
semantics and recomputes the raw-section and Pokémon checksums, plus preserves
all unrelated fields and both bank counters. This Phase17 checker only
compares byte evidence; it cannot serve as that oracle.

Run on a private **computer-side SD copy**, using the separate precomputed
manifest:

```sh
python3 phase17/verify_raw_draft_diff_v1.py \
  --source SD_COPY/3ds/PKSM-Rogue/imports/00000001.sav \
  --draft SD_COPY/3ds/PKSM-Rogue/drafts/phase18_draft_001.sav \
  --independent-manifest /EXTERNAL_VERIFIER/expected_synthetic_edit.json
```

Expected successful output for move research still says
`RAW_BYTES_ONLY_MOVE_RESEARCH_BLOCKED`, **never approval to play**.
A separate `verify_offline_sd_hashes.py` pass must then compare the
`phase18_original_001.sav` and preserved Phase16 container and journal to
**previously recorded, off-SD hashes**. Do not derive a supposed external
reference hash from files immediately after the test.

Host tests `test_verify_raw_draft_diff_v1.py` use disposable synthetic
131072-byte data, no game files or ROMs. They exercise missing/partial
files, stale and changed hashes, wrong expected bytes, extra changed bytes,
aliasing, duplicate JSON fields, malformed manifests, eight-byte move limit,
restart re-verification and no-op rejection. The strict/sanitizer pipeline
also runs inherited Phase14–17 in-RAM rollback tests and existing independent
SHA-256 tests. Python itself is **not** instrumented by ASan/UBSan; only the
C/C++ targets are.

## 3. How your existing authenticated recovery records can help

Phase16's previously authenticated, externally protected full-container copy
can be a **reference snapshot** of what the game-save image originally
contained. Its pre-test SHA-256 and immutable copy support forensic comparison,
distinguishing an offline edit from accidental changes to preserved progress.

**They do NOT yet provide a tested physical restoration procedure.** The
Phase16 rehearsal journal contains simulated before/after images and Phase17
only exercises rollback in RAM. Neither file is a native durable journal
with individually authenticated, transaction-bound terminal receipts.
A successful Phase16 hardware read is not evidence that the 3DS can safely
restore a damaged GBA VC title after a power loss.

Never modify, overwrite, regenerate, rename or feed these archived files to
Phase20. Keep at least two off-active-SD copies and verify their original
local hashes; preserve the entire SD backup separately.

## 4. Requirements for a separate gameplay/restoration research pilot

All are currently **OPEN**, and would require independent QA plus explicit
new user approval before any **disposable progress** is used:

1. **Installed-ROM identity** independently read/proven on that console;
   full v2.1.2 game mapping, move PP table mode, move learnability, PP-Up
   handling, battle cache refresh and all 40 conflicting PP entries resolved.
   A SHA-matched 14040-byte catalogue alone is not live ROM attestation.
2. **Independent semantic edit oracle:** decrypt and validate changed
   party Pokémon, move ID, current/max PP, PP-Ups, PID/OT identity, original
   checksum, sector checksum, both raw banks, and unrelated data preservation;
   confirm no field offsets or variants were guessed.
3. **Authenticated wrapper adapter:** separately reviewed, no-write
   construction/proposal of a **263168-byte** candidate from the complete
   current two-slot authenticated container and exactly one validated raw
   edit; proper target slot, freshness, non-wrapping adjacent wrapper
   counters, title/CID, and genuine console-bound CMAC authentication. No
   CMAC bypass, guessed regeneration or direct raw-to-title rename.
4. **Independent disaster recovery:** two trusted off-console complete
   original containers, preflight source hashes and current installed
   snapshot, *proven* off-SD recoverability, on-device PxiFS0 handle and
   AGB_FIRM persistence semantics, plus a reviewed manual rescue route.
5. **Durable safe transaction protocol:** journal/receipt binding the
   exact before/after bytes and title, versioned verified states, exclusive
   no-overwrite creation, bounded chunk writes/flush/close/readback,
   full-disk/SD removal/power-loss and post-reboot validation. Test only with
   expendable inputs until proven.
6. **Separate physical disposable gameplay pilot:** independent release
   review, owner opt-in, a nonvaluable isolated game/profile and a
   confirmed rollback route, then game loading/re-saving, cross-session
   verification, and independent rollback. Only after these gates may any
   production architecture be discussed; no gate is waived by passing CI.

Phase17 `readonly_status_v1.h` is a **forgeable, shape-checked status-only
C ABI**, with zero native write capabilities. It does not authorise any of
the above, even when showing a positive RAM-rehearsal result.
**`LiveWritesEnabled=false` remains fixed.**
